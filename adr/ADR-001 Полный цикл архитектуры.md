# ADR-001. Обеспечение целостности данных и полного цикла оценки архитектуры

**Статус:** COMPLETED
**Проект:** Architecture MCP
**Область:** SQLite / MCP tools / requirements / facts / assessments
**Приоритет:** Обязательный

## 1. Контекст

Architecture MCP используется как структурированный слой хранения между AI-агентом Goose, требованиями из НПА/ТЗ и фактами об анализируемой архитектуре.

Текущая модель уже поддерживает:

* источники;
* НПА;
* архитектуры;
* атомарные требования;
* атомарные архитектурные факты;
* единый справочник категорий;
* M:N-классификацию требований и фактов;
* assessment требования относительно архитектуры;
* доказательства `SUPPORTS / CONTRADICTS / CONTEXT`;
* confidence;
* rationale;
* SQLite foreign keys;
* WAL;
* транзакции.

При анализе реализации выявлены сценарии, способные привести к логически некорректным данным либо не позволяющие завершить полный жизненный цикл проверки архитектуры.

Настоящий ADR определяет обязательные изменения перед использованием MCP как постоянного хранилища архитектурных знаний.

---

## 2. Решение

В Architecture MCP должны быть реализованы следующие обязательные изменения.

---

## 3. Изоляция поиска фактов по архитектуре

### 3.1. Требование

При выполнении:

```text
fact_search(
    query=...,
    architecture_id=...
)
```

ограничение по `architecture_id` должно применяться ко всем вариантам текстового поиска.

Логика SQL должна соответствовать:

```sql
WHERE (
    ilower(fact_text) LIKE ilower(?)
    OR ilower(COALESCE(normalized_text, '')) LIKE ilower(?)
)
AND architecture_id = ?
```

### 3.2. Причина

Без группировки условий оператором `()` возможно попадание в выборку факта другой архитектуры при совпадении `fact_text`.

Это нарушает основной инвариант:

```text
анализ одной архитектуры
не должен использовать факты другой архитектуры
```

### 3.3. Критерий приёмки

Должен существовать автоматический тест:

```text
Architecture A
  Fact: "Используется PostgreSQL"

Architecture B
  Fact: "Используется PostgreSQL"

fact_search(
  query="PostgreSQL",
  architecture_id=A
)
```

Результат должен содержать только факт Architecture A.

---

## 4. Изоляция evidence assessment по архитектуре

### 4.1. Инвариант

Для каждого факта, связанного с assessment:

```text
assessment.architecture_id
==
fact.architecture_id
```

### 4.2. Проверка должна выполняться

При:

```text
assessment_create(... facts=[...])
```

и при:

```text
assessment_attach_fact(...)
```

### 4.3. Поведение при нарушении

Если факт относится к другой архитектуре:

* операция должна быть отклонена;
* assessment/evidence не должны частично изменяться;
* должен возвращаться структурированный `BAD_REQUEST` или иной специализированный domain error.

Пример сообщения:

```text
Fact 42 belongs to architecture 3,
but assessment belongs to architecture 7.
```

### 4.4. Причина

Без этой проверки может возникнуть формально валидная цепочка:

```text
Requirement
     ↓
Assessment Architecture A
     ↓
SUPPORTS
     ↓
Fact Architecture B
```

Такой assessment является логически недостоверным.

### 4.5. Критерий приёмки

Должны существовать тесты:

```text
assessment_create + fact другой архитектуры → отказ
assessment_attach_fact + fact другой архитектуры → отказ
```

## 5. Повторная оценка требования

### 5.1. Контекст

Assessment определяется парой:

```text
requirement_id + architecture_id
```

Пара должна оставаться уникальной.

Однако архитектурные факты могут дополняться или изменяться.

Следовательно, результат проверки требования также должен иметь возможность изменяться.

### 5.2. Решение

MCP должен поддерживать изменение существующего assessment.

Предпочтительный MCP tool:

```text
assessment_update
```

или семантически эквивалентный:

```text
assessment_reassess
```

### 5.3. Должно поддерживаться изменение

* `result`;
* `rationale`;
* `confidence`;
* связанных facts;
* `relation_type` связанных facts.

### 5.4. Атомарность

Если одновременно изменяется assessment и его доказательная база, вся операция должна выполняться в одной транзакции.

Например:

```text
update assessment result
+
replace evidence facts
+
change SUPPORTS/CONTRADICTS
```

должно либо примениться полностью, либо полностью откатиться.

### 5.5. История assessment

Полная версионная история assessment в рамках данного ADR не обязательна.

История AI-операции должна обеспечиваться через механизм `agent_runs`, описанный в ADR-002.

## 6. Семантика результатов assessment

### 6.1. Поддерживаемые состояния

Минимальный набор результатов должен включать:

```text
COMPLIANT
INCOMPLIANT
PARTIAL
NOT_APPLICABLE
INSUFFICIENT_DATA
```

### 6.2. NOT_APPLICABLE

`NOT_APPLICABLE` используется, если требование было рассмотрено, но не относится к конкретной архитектуре.

Пример:

```text
Требование:
"Для удалённого доступа должна применяться MFA"

Архитектура:
удалённый доступ отсутствует

Результат:
NOT_APPLICABLE
```

### 6.3. INSUFFICIENT_DATA

Используется, когда требование применимо, но имеющихся фактов недостаточно для вывода.

### 6.4. Отсутствие assessment

Отдельный статус:

```text
NOT_ASSESSED
```

не требуется.

Отсутствие записи assessment уже означает, что оценка не выполнялась.

### 6.5. UNKNOWN

Состояние `UNKNOWN` не должно использоваться как синоним `INSUFFICIENT_DATA`.

Если для `UNKNOWN` не определяется отдельная однозначная бизнес-семантика, оно должно быть удалено из `AssessmentResult`.

## 7. Неизменность исходной цитаты

### 7.1. Контекст

Для requirement и fact хранятся:

```text
source_quote
normalized_text
```

`source_quote` является доказательством происхождения записи.

`normalized_text` является интерпретацией.

### 7.2. Решение

Обычные MCP tools:

```text
requirement_update
fact_update
```

не должны позволять изменять `source_quote`.

### 7.3. Допустимое исправление

Если исходная цитата была записана ошибочно, её изменение должно производиться:

* отдельным специализированным tool;
* либо административной операцией с явной семантикой изменения происхождения.

Обычная нормализация или уточнение формулировки не должны менять исходную цитату.

### 7.4. Инвариант

```text
AI interpretation changes
≠
source evidence changes
```

## 8. Миграции схемы SQLite

### 8.1. Контекст

Проект будет развиваться, а рабочая SQLite-база должна сохраняться между версиями MCP.

Использование только:

```sql
CREATE TABLE IF NOT EXISTS ...
```

не позволяет корректно изменять уже созданные таблицы.

### 8.2. Решение

Необходимо реализовать последовательный механизм миграций.

Допустимая структура:

```text
src/architecture_mcp/migrations/
├── 001_initial.sql
├── 002_assessment_integrity.sql
├── 003_agent_runs.sql
└── ...
```

### 8.3. Версия схемы

База должна хранить сведения о применённых миграциях.

Предпочтительный вариант:

```sql
CREATE TABLE schema_migrations (
    version     INTEGER PRIMARY KEY,
    name        TEXT NOT NULL,
    applied_at  TEXT NOT NULL
);
```

### 8.4. Запуск MCP

Последовательность старта:

```text
открыть SQLite
      ↓
прочитать schema_migrations
      ↓
определить неприменённые миграции
      ↓
применить их по порядку
      ↓
запустить MCP server
```

### 8.5. Ошибка миграции

Если обязательная миграция завершается ошибкой, MCP не должен продолжать работу с частично обновлённой схемой.

### 8.6. Сохранность данных

Обновление MCP не должно требовать удаления рабочей SQLite-базы.

---

## 9. Обязательные тесты

В дополнение к существующим тестам должны быть реализованы как минимум:

```text
1. fact_search не возвращает факты другой architecture.

2. assessment_create отклоняет fact другой architecture.

3. assessment_attach_fact отклоняет fact другой architecture.

4. assessment может быть повторно оценён.

5. Повторная оценка атомарно обновляет assessment и evidence.

6. NOT_APPLICABLE принимается как корректный result.

7. source_quote невозможно изменить обычным update tool.

8. Новая БД автоматически получает актуальную схему.

9. Существующая БД старой версии автоматически мигрируется.

10. Уже применённая миграция повторно не выполняется.
```

---

## 10. Последствия решения

Положительные последствия:

* невозможность смешивания фактов разных архитектур;
* корректная работа поиска;
* возможность обновлять оценки после появления новой информации;
* явное различение неприменимости и недостатка данных;
* сохранение исходной доказательной базы;
* возможность безопасно развивать модель SQLite;
* подготовка базы к длительному накоплению данных.

Стоимость решения:

* появление механизма миграций;
* небольшое увеличение логики validation;
* необходимость новых тестов.

Эти затраты считаются оправданными, поскольку изменения предотвращают появление логически неверных либо трудно исправимых данных.
